6. La regla @nx/enforce-module-boundaries de ESLint sirve para evitar dependencias circulares
    Añade la propiedad tags en el archivo project.json de cada uno de tus proyectos. Esto define el rol y ámbito de cada aplicación o librería.

    Backend (apps/exp-shop-server/project.json):

    {
        "name": "exp-shop-server",
        "tags": ["scope:backend", "type:app"]
    }

    Frontend (apps/exp-shop-web/project.json):

    {
        "name": "exp-shop-web",
        "tags": ["scope:frontend", "type:app"]
    }

    Librería TS Compartida (libs/shared/interfaces/project.json):

    {
        "name": "shared-interfaces",
        "tags": ["scope:shared", "type:util"]
    }

    Librería UI de Angular (libs/shared/ui/project.json):

    {
        "name": "shared-ui",
        "tags": ["scope:frontend", "type:ui"]
    }


Abre tu archivo de configuración raíz de ESLint (eslint.config.js, eslint.config.mjs o .eslintrc.base.json). Busca la regla @nx/enforce-module-boundaries y ajusta el arreglo depConstraints:JavaScript"@nx/enforce-module-boundaries": [
  "error",
  {
    "enforceBuildableLibDependency": true,
    "allow": [],
    "depConstraints": [
      {
        "sourceTag": "scope:backend",
        "onlyDependOnLibsWithTags": ["scope:backend", "scope:shared"]
      },
      {
        "sourceTag": "scope:frontend",
        "onlyDependOnLibsWithTags": ["scope:frontend", "scope:shared"]
      },
      {
        "sourceTag": "scope:shared",
        "onlyDependOnLibsWithTags": ["scope:shared"]
      },
      {
        "sourceTag": "type:app",
        "onlyDependOnLibsWithTags": ["type:util", "type:ui", "type:feature"]
      },
      {
        "sourceTag": "type:util",
        "onlyDependOnLibsWithTags": ["type:util"]
      }
    ]
  }
]
Efecto directo: Si intentas importar componentes de Angular (scope:frontend) dentro de NestJS (scope:backend), ESLint marcará un error de compilación.

9. Installing prisma adapter:

  npm install pg @prisma/adapter-pg
  npm install -D @types/pg

  Desde la raíz del monorepo: npx prisma init --datasource-provider postgresql (respeta tu .env existente).
  Mueve el schema.prisma generado a libs/backend/prisma/src/lib/schema.prisma.
  Edita el prisma.config.ts que se generó en la raíz para que su propiedad schema apunte a esa nueva ruta, y define el output del generador hacia algo como libs/backend/prisma/src/generated, para que el cliente generado quede asociado a esa lib backend-only y no se mezcle en node_modules.
  Todos los comandos (prisma migrate, prisma generate, prisma studio) se siguen corriendo desde la raíz — prisma.config.ts es el que le dice dónde está el schema real.

  npm i --save-dev @types/node
  npm install @prisma/config dotenv
  npm install --save-dev prisma dotenv

  Haz las configuraciones necesarias en path y schema en prisma.config.ts:

  import "dotenv/config";
  import { defineConfig, env } from "prisma/config";

  export default defineConfig({
    schema: "libs/backend/prisma/src/lib/schema.prisma",
    migrations: {
      path: "libs/backend/prisma/src/lib/migrations",
    },
    datasource: {
      url: env("DATABASE_URL"),
    },
  });

10. Createa user model in schema.prisma:
  model User {
    id        String @id @default(uuid())
    fullName  String
    email     String   @unique
    password  String
    roles     String[] @default(["user"])
    isActive  Boolean  @default(true)
    createdAt DateTime @default(now())
    updatedAt DateTime @updatedAt

    @@map("users")
  }

11. Execute:
  npx prisma migrate dev --name init_user

  Migración aplicada correctamente contra tu base de Neon.

  Se creó la tabla users en neondb (columnas id, fullName, email, password, roles, isActive, createdAt, updatedAt, con el índice único en email).
  El archivo quedó en libs/backend/prisma/src/lib/migrations/20260917205548_init_user/migration.sql, correctamente ignorado por git al ser parte del código versionable (las migraciones sí se commitean — a diferencia del cliente generado, que dejamos en .gitignore).
  Prisma regeneró el cliente automáticamente después de migrar, así que PrismaService ya tiene el modelo User sincronizado con la base real.
  Con esto, exp-shop-server ya puede inyectar PrismaService en un módulo/servicio y hacer this.user.findMany(), this.user.create(...), etc. contra la tabla real. Avísame cuando quieras armar el primer endpoint/CRUD de User o seguir con otro modelo.
